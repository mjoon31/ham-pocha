# 개발 흐름과 역할

## 운영 순서

`문제·요구 → 사실 확인 → AI 조사/대안 → 개발자 결정 → 계획·범위 확정 → 실행 → 테스트 → 문제 해결·결정 기록`.

개발자는 Game Director / AI Lead로서 게임 방향·우선순위·기술·범위·핵심 리뷰·공개를 결정한다. AI는 조사·초안·구현·검증·분석을 지원한다. 역할별 작업은 한 작업 흐름 안에서 수행하며 문서의 역할 구분이 별도 에이전트 실행 지시는 아니다.

| 단계 | 입력·할 일 | 다음 단계로 넘어갈 조건 | 원본 |
|---|---|---|---|
| 환경 확인 | Git·권한·Unity·조사 접근 상태 | 확인/실패/미실행 구분, 없는 도구와 권한 정리 | Project Status, Source Access |
| 조사 | 원문·리뷰·경쟁작·미충족 요구 | 실제 출처·표본·가설·한계와 개발자 검토 | Research |
| 기획 | 후보 3안·터치 UX·범위·일정 | 게임 선정과 GDD/MVP 승인 | Planning, Decisions |
| 설계 | 구조 2안·기술 비교·위험 PoC | 개발자 기술 선택, 핵심 위험 검증 또는 명시적 조건 | Architecture |
| 구현 | 승인 기능·작은 변경·로그 | 범위 만족, 관련 검사와 환경별 결과 기록 | Issue/PR, Test |
| QA | 실기기·플레이테스트·결함 | P0 결함 해결·동일 조건 재검증, 잔여 위험 정리 | Test, Troubleshooting |
| 전달·공개 | 빌드·설치 안내·정제된 소개 | 실제 대상/자료 검토와 해당 외부 행위 승인 | Publishing |

현재는 환경 확인·조사·기획 단계다. 문서 체계를 만드는 작업은 게임 선정·기술 채택을 대신하지 않는다.

## 작업 시작

1. `git branch --show-current`로 `dev`인지 확인한다. `main`이면 수정 전에 `dev`로 전환한다. 별도 작업 브랜치는 만들지 않는다. `AGENTS.md`, 현재 상태, 관련 규칙을 읽는다.
2. 요청과 기존 승인·결정을 확인한다. 읽기·로컬 정리·승인된 구현을 반복 승인 절차로 막지 않는다.
3. 영향 파일·테스트·불확실성을 알리고 작업한다. 새 기술·범위 확대·외부 행위는 해당 결정만 분리한다.
4. 환경이 없으면 가능한 검증은 수행하고 미실행 항목의 이유·다음 실행 조건을 적는다.

## 결과 보고

완료한 변경 → 실제 확인 근거 → 실행 검사와 결과 → 남은 문제 → 다음 결정 순서로 간단히 보고한다. 과정은 [이슈 기록](../Issue_Records/README.md)에 요청→AI 제안→개발자 결정→실제 수정→테스트·검수→최종 판단 순으로 남긴다. 이슈 발생·재수정은 같은 기록의 다음 회차에 누적한다. 상세 기술·테스트 원본은 링크해 중복을 줄인다.

## 승인 관리

작업 원본은 ham-pocha-dev 하나다. 공개 ham-pocha에서 개발·일상 편집하지 않는다. 공개 동기화 흐름 (공개 제외)에 따라 기능별 원본 커밋안 하나를 제시한다. 공개에는 민감 파일/위치를 제외한 같은 커밋·실제 개발 기록을 반영하며 별도 공개 기획/본문을 만들지 않는다. 승인 후 비공개 dev commit/push부터 공개 반영 확인까지 진행한다. 신규 공개 파일/범위는 먼저 승인받는다. 피드백 수정은 같은 IR의 다음 회차와 새 결과·커밋안으로 연결한다. 비공개 PR은 개발자가 검토·병합하고 그 main 자료의 공개 PR/main 반영은 상시 승인된 자동화다.

개발자의 명시적 지시가 현재 범위를 포함하면 승인으로 취급한다. 승인 기록은 날짜·대상·범위·조건을 남긴다. AI가 대신 최종 승인 체크를 채우지 않는다. 범위를 벗어난 항목은 초안을 검토 가능한 상태까지 준비한 뒤 결정받는다.
