# 결정·문제 해결·협업 기록 규칙

## 목적과 작성 방식

작동 원리, 선택 이유, 실패 원인, 수정과 검증을 다음 작업자가 재현할 수 있게 남긴다. 기록은 개발 업무의 일부이며 공개 문구도 실제 문제와 개선 내용을 설명한다. 프로젝트 파일명·제목·라벨·본문에는 설계·운영·문제 해결을 직접 설명하는 이름을 사용한다. 개발 외 활용 목적이나 독자 평가 목적을 나타내는 수식어는 쓰지 않는다.

## 연결 관계

`R-ID(실제 관찰) → F-ID(GDD 기능) → DEC/ADR(결정) → Issue → PR/commit → T-ID(검증) → 후속 개선`.

- ID는 실제 항목 생성 시 발급한다. 양식의 접두어는 실제 번호나 완료 항목이 아니다.
- 원본 링크를 유지하고 문서마다 같은 상세 내용을 복사하지 않는다.
- GitHub 항목이 아직 없으면 로컬 문서로 시작하고 `Issue/PR 미생성`을 표시한다. 나중에 실제 링크를 추가한다.

## 기록 선택

| 내용 | 위치 |
|---|---|
| 요청·제안·결정·실제 수정·검수·최종 판단·재수정의 시간순 과정 | [Issue Records](../Issue_Records/README.md) |
| 게임·범위 선택 | `Docs/Decisions/` |
| 기술 대안·채택·교체 | `Docs/Architecture/ADR-*` |
| 실행 결과·실패·재실행 | `Docs/Test/Logs/` |
| 재현 가능한 버그·원인·수정 사례 | `Docs/Troubleshooting/Cases/` |
| AI 제안·개발자 판단·실제 반영 | [Collaboration Log](../Workflow/Collaboration_Log.md) |

한 작업은 하나의 이슈 기록에서 회차를 누적한다. 단순 후속 수정마다 장문의 사례 문서를 만들지 않는다. 중요한 실패·비교·재발 방지·기술적 절충만 [문제 해결 양식](../Troubleshooting/Issue_Resolution_Template.md)으로 상세 분석하고 이슈 기록에서 링크한다.

## 최소 내용

문제·기대/실제 → 환경·재현 → 관찰 로그 → 가설과 반증 → 대안·비용 → 개발자 선택과 이유 → 코드/설정 변경 → 같은 조건의 재검증 → 남은 위험·재발 방지.

AI가 분석/구현한 일과 개발자가 직접 결정·수정·실행한 일을 구분한다. 승인되지 않은 제안을 개발자 결정으로 기록하지 않는다. 실패를 숨기거나 성공한 수치만 선택하지 않는다.

개발자 지적을 AI가 수정한 경우와 개발자가 파일을 직접 수정한 경우를 구분한다. 커밋 경위 표시는 [Commit Template](../Git/Commit_Template.md)을 따르고 실제 수정·판단·검증의 주체를 따로 기록한다. 구현 완료·테스트 통과·개발자 수락은 별개 상태다.

## 공개

공개 Git 저장소는 공개 규칙 (공개 제외)에 따라 실제 개발 기록을 원본 경로·회차·내용으로 반영하고 민감 파일·위치만 제외/가림 처리한다. 별도 공개 소개나 AI 협업용 서사로 다시 기획하지 않는다. 개발자 지시·선택, AI가 작성한 결과, 피드백과 재수정, 문제 해결, 개발자 직접 수정, 실제 검증·수락 상태를 보존한다. 원시 대화 덤프·비밀·개인정보는 공개하지 않는다. 별도 사이트의 승인된 요약 정책과 구분한다.
