숲과 마을을 오가며 포차 영업에 필요한 재료를 수집하고, 손님의 주문에 맞춰 조리하고 서빙합니다. 자정이 되면 영업을 마감하고, 집에서 피로를 회복하며 다음 날을 준비합니다. 영업으로 얻은 골드와 경험치는 음식 강화와 새로운 탐험 지역·레시피 해금에 쓰입니다.

## 숲에서 포차까지, 햄스터의 하루

**숲 탐험·재료 수집 → 재료 입고 → 조리·서빙 → 판매·성장 → 마감·수면**

- **계절 숲 탐험**에서는 미니맵으로 출입구와 수집 대상을 확인합니다. 밤에 몬스터가 공격해 오면 채집을 더 이어갈지, 모은 재료를 가지고 돌아갈지 판단합니다.
- **실내 조리와 서빙**은 공유 냉장고에서 재료를 꺼내 조리대에 넣는 것부터 완성된 음식을 손님에게 직접 건네는 것까지 이어집니다.
- **야시장 영업**은 화로에서 꼬치를 구워 진열하고 자동으로 판매하는 방식입니다. 판매 수익과 경험치로 음식을 강화하고, 새 메뉴와 화로, 탐험 지역을 엽니다.
- **집 꾸미기**에서는 창고에 보관한 가구의 위치와 방향을 바꾸고, 벽 마감을 바꿔 공간을 꾸밉니다.

## 플레이를 받치는 구조

- **씬 전환과 영업 진행.** 공통 시스템이 있는 Main 씬을 유지하고 집·마을·숲을 필요에 따라 불러옵니다. 실내외 영업 중에는 마을과 포차 씬을 함께 두고 카메라와 조작 대상을 전환해, 다른 공간의 조리와 손님 행동도 이어지도록 구성했습니다.
- **레시피·성장 데이터.** 레시피에 재료와 아이콘을 연결하고 콘텐츠 카탈로그에서 메뉴 해금과 강화를 관리합니다. 조리·메뉴 선택·강화 화면이 같은 데이터를 참조합니다.
- **탐험과 미니맵.** 이동과 상호작용은 Unity Input System으로 처리합니다. 숲에 다시 들어오면 채집 대상과 몬스터를 재배치하고, 같은 방문의 저장을 이어갈 때는 수집 상태를 복원해 미니맵에도 반영합니다.
- **가구 배치와 계정별 저장.** 배치 전 격자의 점유와 입구·침대 접근 경로를 확인합니다. 로컬 JSON과 Firebase Authentication·Cloud Firestore를 연결해 계정별 진행을 저장하고, 저장 ID로 주문 상태와 가구 배치를 복원합니다.

## AI 개발 하네스와 작업 흐름

게임의 방향, 구현 우선순위, 기술 채택과 최종 검수는 제가 맡았습니다. AI에 작업을 맡기기 전에 **프로젝트 지침, 역할별 Codex 대화, Unity MCP, 공용 작업 메모와 검증 기록**을 연결했습니다. 이 개발 하네스는 작업마다 AI가 어디서 기준을 찾고, 무엇을 수정할 수 있으며, 어떤 결과를 확인해야 하는지 정해 주는 작업 환경입니다.

**역할과 범위 지정 → 관련 지침·현재 상태 확인 → 충돌 확인 → 구현·검증 → 같은 기록에 피드백과 결과 반영**

1. **작업을 지시하기 전에 기준을 정했습니다.** 기능 개발·기획 문서·시장조사·비주얼 디자인·모델링·애니메이션·이슈 기록·Git/공개 관리를 8개 대화 역할로 구분했습니다. 새 대화에는 목표, 기준 문서나 이슈, 산출물, 확인 가능한 완료 조건을 넘겼습니다. 루트 `AGENTS.md`에서 공통 제약과 작업별 지침을 찾게 하고, 작업에 따라 확정 기획·코딩·UI·테스트 규칙을 확인하도록 했습니다. Unity 작업 전에는 열린 프로젝트를, Git 작업 전에는 브랜치와 변경 내용을 확인하는 절차를 뒀습니다. Unity MCP는 에디터 상태 확인과 컴파일 검사에 사용했습니다.
2. **컨텍스트 윈도우에는 판단에 필요한 내용부터 넣었습니다.** 첫 요청은 관련 기능·이슈·코드에서 시작하고, 후속 요청은 마지막으로 확인한 커밋과 기록을 기준으로 새로 바뀐 부분을 읽었습니다. 긴 로그나 대화 전문은 옮기지 않고, 기준 커밋·결정·대상 파일·검증 링크를 작업당 공용 메모 한 장에 남겼습니다. 새 대화에서는 작업 ID나 이슈 기록으로 이어받고, 실제 수정 전에는 대상이 최신인지 다시 확인했습니다.
3. **중복 구현과 파일 충돌을 작업 전에 확인했습니다.** 같은 기능의 후속은 기존 대화와 이슈 기록에 이어 쓰고, 끝난 조사·검증은 조건이 같으면 근거를 재사용했습니다. 작업 메모의 수정 예정 파일과 Git의 미커밋 변경을 대조하고, 겹치는 범위가 있으면 해당 수정만 멈춰 순서를 조율하는 규칙을 두었습니다. 저장 ID 부여나 레시피 참조 검사도 기존 Unity 에디터 도구와 사용 안내를 먼저 확인했습니다.
4. **의사결정과 공개 권한을 구분했습니다.** AI는 승인한 범위에서 조사·구현·검증을 진행하고, 게임 규칙·범위·기술 변경과 공개 여부는 제가 결정했습니다. 작업 기록에는 개발자의 판단과 직접 작업, AI의 수정과 검사, 실행 환경을 구분했습니다. 공개 동기화에는 파일별 허용 목록을 적용했습니다. [커밋 양식](https://github.com/mjoon31/ham-pocha/blob/dev/Docs/Git/Commit_Template.md) · [공개 동기화 과정](https://github.com/mjoon31/ham-pocha/wiki/AI-Automation)
5. **다음 작업에서도 검증 근거를 다시 쓸 수 있게 남겼습니다.** 요청 → AI 제안 → 개발자 결정 → 변경 → 검증·피드백을 같은 이슈의 후속 회차로 이어 갔습니다. 컴파일·Unity 편집 모드·실제 플레이·Android 실기기 결과를 구분하고, 실행하지 않은 검사는 `NOT RUN`으로 남겼습니다.
